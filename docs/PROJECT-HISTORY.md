# 共享项目历史、内置 Git 与安全回退

> **路线更新（2026-11-13）：合作仅走 GitHub；NAS 适配器、在线提示和工具已清理。** 普通 App 工作流已接入源码，但已配置公共 GitHub App 标识，但真实双账号协作和正式安装验收仍需实际验证。GitHub 共享明确同步的提交，本机保存日志不自动上传；旧项目和历史数据没有删除。使用见[合作指南](<GITHUB-WORKFLOW.md>)，当前边界见[交接说明](<HANDOFF.md>)。

## 两个人看到什么

- **本机保存版本**：成功保存/新建/回退，在本机项目 `.paperstudio/history-v1` 追加前后内容和记录。这些记录是本地恢复依据，不自动传给合作者；NAS 同目录合作已取消。
- **GitHub 中转**：软件已内置 isomorphic-git，不要求系统 Git。明确保存快照/同步后，另一端获得同一仓库提交，在文件版本界面查看提交作者、时间、逐文件差异并回退文件。
- 本机保存日志与 GitHub 提交是两种来源，不是自动双向桥；尚未明确同步的逐次保存不会自动上传。旧 NAS 私有镜像实现已移除，已有缓存没有自动删除。
- 手工仓库/PAT 操作只属于独立开发者区；普通登录/私有项目/邀请/加入/同步源码已接线，不要求 PAT，但不等于已完成真实账号或正式安装验收。

## 修改者与差异

软件保存记录显示当前操作系统显示名，**未经身份认证**；这不是不可篡改审计日志。共享目录写权限持有者能修改历史，不能用于不可信双方的责任认证。
Git 记录显示的是**提交作者**，并不证明提交内每一行由该人编辑。

已有文件首次进入文件版本历史时，先保存“原始内容（作者未知）”。如果磁盘内容与上一条记录不同，下次软件保存前会保留“外部修改（作者未知）”基线，不冒认成当前保存者；外部工具两次连续改写之间未被观察的中间内容无法重建。只读刷新不会替所有外部修改即时创建记录。

## History 界面（0.3.5）

交互结构参考 [Overleaf 官方 History 文档](https://docs.overleaf.com/writing-and-editing/history-and-versioning)：打开“修改历史”进入独立只读视图，左侧选择有记录的文件，右侧按时间倒序选择版本，中央以行号和绿／红背景显示该版本的新增／删除，保留普通上下文并自动定位第一处改动。上下箭头跳转改动位置；比较起点可选择同一文件的较早版本。“返回编辑”或 Escape 回到原缓冲区，不重读或覆盖未保存草稿。

初始记录没有可比前版时显示普通源码，不把全文标为新增。显示最多 120000 字符／1200 行，超过边界明确提示不是完整比较；回退仍使用完整已验证内容，不把显示差异或截断文本写回文件。

这不是 Overleaf 的全项目时间快照：本机后端只支持逐文件记录和回退。因此不提供虚假的全项目还原、标签或多人实时编辑归因；比较起点的选择也不会改变恢复目标。

## 回退的精确含义

1. 选中一条**文件版本**，可以回退该文件至该条记录的“此版本”全文。
2. 当前草稿必须先保存，或取消回退保留草稿；不提供借回退静默丢弃草稿的路径。
3. 界面读取目标文件当前 SHA-256，并经过界面与原生确认。确认期草稿变化会停止回退；写锁内最终再次校验磁盘版本，不匹配就报冲突。
4. 回退产生新 `restore` 记录，含回退前/后正文；旧记录仍在。其他文件不回退。

**尚不支持整个项目快照一键还原、恢复已删除文件、二进制回退。** Git 视图只列出当前仍存在且可安全读取的支持文本文件，最多读取 100 个 HEAD 可达提交、列出 200 条文件记录；merge 以第一父提交比较，窗口外版本不通过任意对象 ID 访问。
Git 对象大小限制发生在 isomorphic-git 解包之后，不能称为硬解压/内存隔离。目录遍历、显示内容、累计读取均有限额。

## 保存协议与失败

[项目服务](<../client/src/main/local/project.ts>)在新建/保存/回退前通过[项目锁](<../client/src/main/local/write-lock.ts>)原子创建项目根的 `.paperstudio-write-lock`，同一项目的合作客户端排队执行最终版本检查、历史准备、写入、读回和历史提交。

- 等待约 2 秒仍有锁则拒绝本次写入，保留草稿；**不按时钟、心跳、本机 PID 或锁龄抢锁**。
- 锁只约束遵循本协议的软件客户端；任意外部编辑器/脚本不受锁约束，仍存在最后检查与外部写入的竞态，不能宣称通用文件系统原子 CAS。
- [共享历史](<../client/src/main/local/version-history.ts>)先保存内容哈希对象与 pending，实际文件写后核对，再发布记录。失败可能发生在文件已落盘之后，因此错误会要求保留草稿并读取比较，不能把“没有收到成功”解释成“磁盘一定没变”。
- 后续写事务只在当前文件哈希明确等于 before/after 时恢复 pending；其他内容、根目录/父目录不可达、链接/哈希/记录损坏均保留证据并拒绝继续，绝不盲删。
- 列表仅展示已提交记录，不在浏览时恢复活跃事务。并行提交可能导致一次可重试读取失败，重试刷新即可；不因此覆盖正文。

## 备份、空间与残留锁恢复

历史正文保存在项目目录内，应与论文一起备份、继承论文保密访问范围，不要上传公开仓库；该目录不进入普通 GitHub 同步或 TeX 编译快照。
默认历史配额 128 MiB、10000 条记录，内容按 SHA-256 去重；满额停止保存，不自动删除历史。当前没有图形化归档/回收历史功能，不建议长期高频写入大文件。

崩溃可能留下项目锁，软件不会自动解除。管理员恢复的先决条件：

1. 停止使用该本机项目目录的全部客户端及其他写入程序，确认磁盘与文件系统可稳定读取。
2. 完整备份项目、正文、`.paperstudio/history-v1` 和锁目录；不要仅备份当前正文，也不要删 pending 来消除报错。
3. 人工核对正文、pending 与前后哈希；无法确认时保留所有证据并求助维护者，不操作现有论文试错。
4. 仅在确认没有活跃写入者后人工处理残留锁；重新打开项目、读取磁盘比较，保留原草稿副本，再尝试一次受控保存。

本软件没有“强制解锁/覆盖”按钮，也不提供对未知锁的自动删除命令。

## 验证边界

本轮完成真实本机文件/多进程竞争、崩溃锁不抢占、pending 恢复/歧义/根与父目录断开模拟、真实临时 Git 仓库、dirty/原生确认 epoch 和 DOM 回退回归。
开发版 Electron 图形 smoke 单独记录，不等于原样安装包、真实 NAS 或第二台电脑。
用户当前只有本机、无代码签名资源；真实双方 GitHub 账号和[正式发布安装](<RELEASE-ACCEPTANCE.md>)保持待验收，不用本机模拟凑通过。旧截图／结果记录已按用户确认删除，不能把历史 hash 当作当前证据。
